## Narrowly scoped DEV classification and exclusion

After this audit, the user approved a guarded DEV-only owner test on 20 October 2026. Eleven migrations `20261020010000` through `20261020110000` were independently verified, installed only in hosted DEV, and passed the isolated migration-stack check. The seventh holds the fictional employer and vacancy identity fixed after classification; the eighth excludes linked qualification and preference rows from direct ordinary staff/export reads; the ninth keeps fictional résumé objects owner-readable but out of ordinary staff download/export paths; the tenth blocks employer attendance in official events; the eleventh blocks fictional employer/vacancy attribution on genuine interviews and outcomes. The designated fictional account is now classified in one audited, time-bounded case with a fictional employer and vacancy. Anonymous API checks confirm the vacancy is hidden from public listing and detail routes. Signed-in owner acceptance and broader hosted staff/export/pair-vector regression remain pending; see `DEV_GUARDED_TEST_ACTIVATION.md`. Earlier statements in this audit about an absent registry or unclassified account describe the **pre-activation** observation.

1. Add a **private, server-owned** registry for explicitly approved synthetic test identities, keyed by immutable Auth user ID and resolved through `participants.auth_user_id` to participant ID. Required fields: purpose, classification (`approved_synthetic_test`), authorized by/at, DEV project ID, permitted test period, scope (`owner_profile`, `synthetic_recruitment`), ticket/decision reference, and status/revocation timestamp. Restrict reads to approved administrators and writes to a privileged audited approval procedure. Email, name, user metadata, a client flag, and a `@example` domain are not trustworthy classifiers. A record with no approved entry stays **unclassified**; the present account has no approved entry.
2. Bind any synthetic employer, vacancy and event to the same approved test case, with an explicit reciprocal synthetic scope. Owner self-service may read/edit its profile, owned private resume, and its synthetic case history. Ordinary employer/PESO candidate matching, referrals, event selections, contact lists, provider requests and official reports should exclude the synthetic participant. A synthetic-only testing view may include the paired test actors with clear labels; it must never be selectable as an ordinary employer, official event, public job, or real referral destination.
3. Enforce exclusion **at server boundaries**: candidate-pool and semantic RPCs; individual pair/keyword RPCs for synthetic-to-genuine pairings; managed extraction source/begin and embedding generation; metrics/program RPCs; `registrants`-based lists and report/export sources; event assignment/referral/application entry to genuine cases. Apply the predicate by participant ID before aggregation, pagination, ranking, export, or provider call. Do not rely on UI filtering or RLS changes that would remove owner access. Reject a synthetic actor applying to a genuine vacancy; retain existing formal applications and audit history if classification is later revoked.
4. For historical safety, use the same registry to exclude already created linked records from ordinary reports and rankings while keeping them queryable in audited case-history views. Mark generated embeddings/suggestions as restricted; do not delete them without retention/disposition approval. Reconcile earlier downloaded exports and backups separately; they cannot be retroactively changed by a database filter.
5. Test the proposed boundaries with two synthetic identities, one genuine-shaped control record **only in an isolated fixture**, and a paired synthetic employer/vacancy. Verify unclassified and revoked statuses have no synthetic privilege; ordinary counts exclude approved synthetic rows before denominators; owner history retains withdrawn applications; cross-account and genuine-employer routes deny. Independently review SQL and access grants before any DEV migration. Do not activate a classification or rewrite live records through this proposal.
